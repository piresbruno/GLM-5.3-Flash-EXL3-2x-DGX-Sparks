# R1 freeze forensics — 2026-08-30 pinned-boot freeze (dgx1)

Boot: `KV_CACHE_MEMORY=15724154880` (14.64 GiB pin = to-fit 15.64 GiB − 1 GiB
margin), CACHE_FLUSHER=1, R1 bundle (MNBT 3584 / LPT 1792 / async off /
retention 0). Log: `logs/r1-boot2-pinned.log`.

## Verdict

**OOM — but at the NVRM driver level, not the Linux OOM-killer.** The frozen
boot's kernel journal (`journalctl -k -b -1`) contains **68
`NV_ERR_NO_MEMORY`** failures — the NVIDIA kernel driver failing to allocate
physical memory for GPU context buffers:

```
NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY]
  (0x00000051) returned from kgrctxAllocMainCtxBuffer(...) @ kernel_graphics_context.c:1387
NVRM: ... _memdescAllocInternal(pMemDesc) @ mem_desc.c:1359
```

On GB10 UMA the NVRM allocations come from the same physical RAM as everything
else. The pin reserved 14.64 GiB non-reclaimable at engine init (auto leaves
~3.7 GiB unallocated between to-fit 15.64 and in-use 11.94), so when the API
server bring-up / multi-modal warmup created new CUDA work, NVRM could not get
pages, entered an assertion storm, and the host froze.

## Timeline (frozen boot, head kernel journal)

| Time (Aug 30) | Event |
|---|---|
| ~05:11 | boot2 launched (pinned) — ritual clean, MemFree ~121 GiB both nodes, flusher sidecars up |
| ~05:02–05:18 (container clock 04:32–04:33) | weight load done; pin reserved 14.64 GiB; pool 1,179,591 tokens (1.97×); graphs captured (1.88 GiB); engine init 49.56 s |
| **05:19:28** | first `NV_ERR_NO_MEMORY` — exactly at the last boot-log line (API server bring-up / MM warmup window) |
| 05:19–05:33 | thrash valley: flusher fires `drop_caches` every ~5 s (MemFree < 8 GiB trigger) but page cache was already small — the deficit was structural (the pin), so flushing could not save it |
| **05:33:15** | journal ends — host froze; power cycle required. dgx1 `up 4 min` at inspection |

dgx2 stayed SSH-accessible through the dgx1 freeze (operator observation) but
was rebooted ~20 min later; its `glm53-exl3-worker` container exited cleanly
(0) at the worker's shutdown. Worker MemFree after reboot: 119.5 GiB free.

## This signature precedes EVERY freeze on this kit

`journalctl -k -b -1` on the head (journal persists across reboots) shows the
`NV_ERR_NO_MEMORY` storm across the whole campaign: 66 lines on Aug 29
(13:52 userspace OOM-killer kills `VLLM::Worker_TP` → 14:41 first NVRM OOM →
20:46 the C4 17.7 GiB-pin freeze) and 2 on Aug 30 (today). Auto-pool boots
(11.94 GiB in use, no reservation) have never produced this signature.

## Causal chain (why it keeps happening)

1. Campaign math re-derives a pin from the envelope ("to-fit looks safe") —
   but to-fit counts the slack the boot itself still transiently needs.
2. Pin skips the profiler and reserves upfront from MemFree → the auto path's
   slack becomes a structural deficit.
3. The post-init window (API bring-up → head-only MM warmup burst → shape
   warmup) creates new CUDA contexts/work → NVRM asks for physical pages →
   `NV_ERR_NO_MEMORY` storm → UVM/driver stall → hard freeze.
4. drop_caches cannot help at that point: page cache is already flushed; the
   deficit is non-reclaimable reservations. Prevention must be structural:
   **no pins on this kit** (auto pool = 963,265 tokens = 1.61× the 600k
   window), plus drain the load's page cache BEFORE the warmup burst, and
   keep the flusher alive until the fleet is serving-stable.

## Decision (operator, 2026-08-30)

- KV pin REJECTED; auto pool adopted. Pins require `ALLOW_KV_PIN=1` (hard
  guard in start.sh).
- Vision stays on; MM warmup re-sequenced after a post-init cache drop.
